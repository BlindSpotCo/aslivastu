## What AsliVastu is
A Delhi NCR neighborhood livability scoring product. The pipeline (`nqr_delhi`, GitHub `gurshaansb/aslivastu-pipeline`) scrapes/hardcodes data across 8 categories (air, crime, infrastructure, power, water, roads, sewerage, schools) per PIN code and computes an "NQI" (Neighbourhood Quality Index, 0–100) with a letter grade. The frontend (`nqr-web`, GitHub `gurshaansb/aslivastu-web`, deployed on Vercel, live at www.aslivastu.com) is a Next.js Pages Router app that reads the pipeline's output JSON and renders it.

## Critical operational facts (don't relearn the hard way)
- No network access from the sandbox to github.com or npm. Cannot `git push` or `npm install` — always give the user copy-paste terminal commands to run themselves.
- Vercel does NOT auto-deploy on git push for this project (deployed via Vercel CLI, not GitHub integration). After every push the user MUST run `npx vercel --prod` from `~/nqr-web` to publish. A bare `git push` changes nothing live.
- Vercel edge-caches aggressively. Right after a deploy, the live URL can still show old content. Append `?cb=<new-number>` (change the number each time) to bypass, or hard-refresh.
- Stale git lock files recur (`.git/index.lock` etc.). Fix: user runs `rm -f .git/*.lock`, then retries. The sandbox cannot delete them.
- Don't run git commit/push directly from the sandbox — no author identity, no network. Always hand the user exact commands.
- Data flow: pipeline writes `nqr_delhi/data/processed/*.json` → manually copied to `nqr-web/public/nqi_scores.json` and `public/master_by_pin.json` → committed → deployed. No automatic sync between repos.
- `nqr_delhi/.gitignore` ignores `data/raw/*.json`, `data/processed/*.json`, and `*.csv` (they're scraper dumps). The curated price file is an exception and must be force-added.

## What was just done this session — Issue #7 "No connection to price" (from the 16-issue list)
Goal: connect the livability score to property price. Approach mirrors the crime_percentile pattern: **informational, clearly labeled, deliberately NOT folded into the NQI composite** — avoiding the same false-precision trap avoided with per-capita crime.

Data source = government circle/collector rates (the legal minimum property valuation for stamp duty), which genuinely exist at locality/sector resolution. Verified this session that all regions have usable data: Delhi (MCD Category A–H, 2014 notification, A ₹7,74,000/sqm → H ₹23,280/sqm), Gurugram (gurugram.gov.in collector rates), Faridabad (faridabad.nic.in), Noida/Gautam Budh Nagar (igrsup.gov.in, sector categories revised Apr 2025: A+ ₹1.75L → C ₹63,650/sqm), Ghaziabad (igrsup.gov.in). ## Working pattern for this project
1. For any UI/feature change involving new data: verify data availability + granularity FIRST (learned the hard way with a population dead-end — don't promise what the data can't support).
2. Make edits directly via Read/Edit on the mounted repo folders (they're the user's real files).
3. Run `npx eslint <file>` after changes; compare error count to baseline; never introduce new errors.
4. Give the user exact git add/commit/push commands (never run git yourself) + a reminder to run `npx vercel --prod`.
5. When something "doesn't appear" live, check in order: (a) was it pushed AND deployed via `vercel --prod`, (b) Vercel edge-cache (`?cb=` buster), (c) only then assume a real bug.
